How it works

Architecture

AI4IA is a governed, multi-model chat and agent app on Azure Container Apps. The web frontend calls the FastAPI backend; the backend owns auth, session state, tools, memory, document/library access, usage metering and all model routing. The editable source of these diagrams lives in docs/architecture.md.

1 · High-level request flow

Compatible HTTP/SSE calls route through SimpleL7Proxy then APIM to a catalog-selected Foundry deployment. Native planes (Content Understanding, Monitor, Cosmos, Storage, Search, Key Vault) are called directly with managed identity. Voice Live connects the browser to the API over a WebSocket because neither the Next.js HTTP proxy nor SimpleL7Proxy proxies WebSockets; the relay calls the APIM realtime API and still enforces auth, Origin, entitlements and metering.

2 · Deployment topology

The live footprint in rg-ai4ia-slurmfactory (East US 2 primary), grouped by role. See the deployment snapshot for exact resources and health.

3 · Identity & RBAC

Azure service data planes use managed identities and scoped roles. Three independently scoped APIM subscription keys separate the proxy-ingress (FastAPI to proxy), proxy-to-model, and realtime (FastAPI to APIM) hops, plus an optional fourth for Speech Voice Live, and all remain Container App secrets. The API identity is the most privileged; see Requirements → Permissions for the full map.

4 · Two MCP tool planes

Remote MCP tools reach the model through two independent planes that share one governed per-turn executor. On a tool-name collision the official tool wins; a single per-turn budget caps total MCP calls across both planes.

5 · Anatomy of a chat turn

The governance order every request passes through: authenticate, gate, plan, route, persist. Telemetry and derived stores are best-effort and never break the turn.
